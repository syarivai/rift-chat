## The constraint everything follows from

Three facts about the API, verified by probe on 2026-09-10:

1. `GET /api/posts?userId=N` filters server-side and returns two or three posts per contact.
2. Every returned post is authored **by the contact**. There is no sender field.
3. `POST /api/posts` returns `201` but **does not persist**, and always returns `id: 101`.

A conversation therefore cannot be a projection of server state — the outgoing half has nowhere
on the server to live. That single fact produces the outbox, the "never invalidate a thread"
rule, and the local-persistence requirement (O-01).

Dependency direction is one-way: `app → features → core`. Slices never import each other. No
barrel files — import the module you mean.

## Data model

```ts
// core/api/types.ts — mirrors the wire format exactly
type Envelope<T> = { total: number; limit: number; offset: number; results: T[] };
type Contact = { id: number; name: string; username: string; email: string;
                 avatar: string; phone: string; website: string;
                 address: { street: string; city: string; zipcode: string } };
type Post = { id: number; userId: number; title: string; body: string;
              tags: string[]; category: string; createdAt: string };

// features/chat/model/types.ts — what the UI actually renders
type OutboxMessage = {
  readonly localId: string;          // client-generated; the server id is always 101
  readonly contactId: number;
  readonly body: string;
  readonly createdAt: string;
} & ( { status: 'sending' }
    | { status: 'sent'; deliveredAt: string }
    | { status: 'failed'; error: string } );

type ThreadMessage =
  | { kind: 'incoming'; id: string; body: string; createdAt: string }
  | { kind: 'outgoing'; message: OutboxMessage };
```

`OutboxMessage`'s status union is the error model. There is no separate `Result` type — it would
describe the same three states twice.

**Mapping**: a `Post` renders as an incoming message using `body` (never `title`, `tags`, or
`category` — mapping those would invent a data model the API does not express).

## API layer

One small `fetchJson` wrapper: builds the URL, sets the JSON header, throws on a non-2xx or a
shape that fails a narrow runtime check. Throwing is deliberate — React Query converts it into
`error` / `isError` / retry, which is what the screens render.

```ts
GET  /api/users?limit=20&offset=N     → Envelope<Contact>
GET  /api/users/:id                   → Contact          (bare, not enveloped)
GET  /api/posts?userId=N&limit&offset → Envelope<Post>
POST /api/posts                       → Post             (id always 101; not persisted)
```

## Query layer

**Client defaults**: `staleTime: 60s` (the API sets `max-age=300`), `retry: 2`,
`refetchOnWindowFocus: false` (meaningless on mobile). NetInfo drives `onlineManager`, so
queries pause offline rather than burning retries.

**Keys** come from one factory — no inline literals:

```ts
queryKeys.contacts.list()       // ['contacts','list']
queryKeys.contacts.detail(id)   // ['contacts','detail',id]
queryKeys.messages.thread(id)   // ['messages','thread',id]
```

**Pagination** is arithmetic, since the envelope carries `total`:

```ts
getNextPageParam: (last) =>
  last.offset + last.limit >= last.total ? undefined : last.offset + last.limit
```

**Profile seeding**: `GET /api/users` already returns every field the profile needs, so
`useContact` supplies `initialData` from the list cache with `initialDataUpdatedAt`. Without
the timestamp the seeded value counts as fresh and the background refetch never runs.

**Invalidation**:

| Action | Invalidates |
| ------ | ----------- |
| Pull-to-refresh on Chats | `contacts.list()` |
| Blocking a contact | nothing — client state |
| **Sending a message** | **nothing** |

The send mutation touches no query. Invalidating a thread refetches the original posts and
deletes every message the user has sent.

## Store layer

One Zustand store, three slices, persisted to MMKV through `persist` + `createJSONStorage`.
MMKV reads synchronously, so the store is hydrated on first render — no flash of an empty
thread or the wrong theme. MMKV v4's API is the `createMMKV()` factory with `remove()`, not
v3's `new MMKV()` / `delete()`.

```ts
outbox:  { byContact: Record<number, OutboxMessage[]>,
           enqueue, markSent, markFailed, retry }
blocked: { ids: number[], toggle }
prefs:   { language: 'system'|'en'|'ms'|'id', theme: 'system'|'light'|'dark',
           setLanguage, setTheme }
```

Selectors are narrow — in a 60-row list a broad selector re-renders every row. Object- or
array-returning selectors are wrapped in `useShallow`.

## The outbox — the one piece with real logic

This is the only part of the app that gets pure functions and thorough unit tests, because it
is the only part with rules that would survive replacing React Query or the UI.

### Merge

```ts
mergeThread(posts: Post[], outbox: OutboxMessage[]): ThreadMessage[]
```

Maps posts to `incoming` and outbox entries to `outgoing`, concatenates, and sorts by
`createdAt` ascending with `localId`/`id` as a stable tiebreaker. **Stability matters**: an
unstable sort makes bubbles jump between renders. Pure — no clock read, no store access.

### Lifecycle

```text
enqueue ──► sending ──► sent
                │
                └────► failed ──(retry)──► sending
```

1. **Enqueue** — `localId` from `newId()`, `createdAt` from the clock, status `sending`,
   appended and persisted. The bubble renders immediately. The message is durable *before* the
   request leaves: the optimism is about delivery, not existence.
2. **`201`** — status `sent`, `deliveredAt` from the response's `createdAt`. No query touched.
   The response `id` is discarded.
3. **Error** — status `failed`. **Not a rollback.** Deleting content the user typed is the
   wrong response to a network error.
4. **Retry** — back to `sending`, request re-issued. Auto-triggered on reconnect (O-04).

Illegal transitions (`sent → sending`, `sent → failed`) are rejected by the reducer and covered
by tests.

## Navigation

expo-router. `(tabs)` group holds Chats and Settings; `chat/[id]` and `profile/[id]` push over
it. Route params arrive from outside the app, so `id` is validated — a non-numeric or unknown id
renders a not-found state rather than crashing or issuing a garbage request.

## Theme

Semantic tokens (`bg`, `surface`, `text`, `textMuted`, `accent`, `bubbleIn`, `bubbleOut`,
`danger`, `success`, …) with light and dark maps over the same keys, so a component reads
`theme.colors.text` and is correct in both. Resolution: explicit choice → OS `useColorScheme()`
→ light. Full scales in [Design tokens](../../docs/reference/design-tokens.md).

## i18n

`i18next` (engine) + `react-i18next` (hook and re-render on language change) +
`expo-localization` (device locale). Catalogs are one flat JSON per locale, namespaced by
screen. Keys describe purpose, never the English text. Malay and Indonesian have no grammatical
plural, so both collapse to CLDR `other`; i18next handles that with no special-casing.
Relative times use `Intl.RelativeTimeFormat` — Hermes ships Intl, so no date library.

## Network and offline

NetInfo wired to React Query's `onlineManager`: offline queries pause instead of failing. An
offline banner renders from the same signal. On reconnect, failed outbox messages are retried
in order.

## Performance

Rules: memoised rows declared outside the parent, no inline arrow props or style objects,
stable `keyExtractor`, `getItemLayout` (row height is fixed), tuned `initialNumToRender` /
`maxToRenderPerBatch` / `windowSize`, and `expo-image` with `recyclingKey`.

Validation is measured, not asserted: render counts before and after memoisation, and
`gfxinfo` janky-frame percentages from the **release** build with a scripted `adb input swipe`.
**Bar: under 5% janky frames.** Missing it after genuine tuning is the trigger in
[ADR 0003](../../docs/explanation/adr/0003-list-rendering-flatlist.md) to reconsider FlashList.

## Testing

| Layer | Covers |
| ----- | ------ |
| Unit | Merge order and stability, the status lifecycle including illegal transitions, relative-time formatting |
| Integration (RNTL + MSW + real `QueryClient`) | Pagination stop condition, optimistic send happy path, failure, retry, store rehydration |
| Component (RNTL) | Composer clears on send, blocked bar replaces the composer, empty states render |
| E2E (Maestro, one flow) | Launch → scroll → open chat → send → restart → message persists → block |

MSW mocks at the network boundary and **reproduces the quirks**: `POST` returns `id: 101` and
does not mutate the collection. A handler that persisted the write would hide the bug the whole
app is designed around. Time is pinned with `jest.setSystemTime()`; MMKV ships its own Jest mock and NetInfo is
`jest.mock`ed.

## Security

No secrets in the bundle. HTTPS only, `usesCleartextTraffic: false`. MMKV is not a secure store
and holds nothing sensitive. No PII or message bodies in logs. Route params validated. Dev-only
affordances guarded by `__DEV__`. Full baseline: the `app-security` skill.

## Risks

| Risk | Mitigation |
| ---- | ---------- |
| Scope overrun — every nice-to-have plus i18n on a 4-day clock | P0/P1/P2 tiers, hard cut at end of day 3 |
| The API changes mid-assessment | `api-contract-verifier` re-probes; the contract doc is the single source |
| Release build differs from dev (minification, missing dev-only code) | The APK is built and smoke-tested on device on day 3, not day 4 |
| Reanimated 4 / worklets misconfiguration | Wired in Phase 0 with a trivial animation, before it is needed |
| Jest 30 or ESLint 10 leaking in and breaking the toolchain | Pinned via `overrides`; documented in [Tech stack](../../docs/reference/tech-stack.md) |
| Translation length breaking layout in ms/id | `qa-tester` sweeps all three locales before submission |
